# 背景

DemoTyper 的智能补全使用“逐字符 + 基于行的 diff”来让当前文件逐步追上目标文件，并在用户输入 `{ ( [` 时保留自动配对与跨行占位闭符（`placeholderClosings`）的能力。

近期出现的两个问题：

1. **死循环**：在某些缺失/删除场景下，Gap 检测与自动配对叠加，导致同一 offset 反复插入 `\n`、缩进、以及 `()`/`{}` 等占位骨架，最终触发插入历史保护。
2. **多余闭符/大括号**：占位闭符被误判为“需要拆行”的残留符号或被重复补齐，造成额外的 `)` / `}`。

本方案目标是在 **不改动自动配对与跨行占位逻辑** 的前提下，仅通过改进 Gap Detection 的分支决策，解决上述问题。

# 核心约束（必须满足）

- **自动配对不能丢**：`(` → `()`，`{` → `{}`（含智能展开），`[` → `[]` 必须保留。
- **跨行符号配对/占位跟踪不能动**：`placeholderClosings` 的添加、消费、漂移修正、外部删除通知等现有机制保持不变。
- 本方案只调整“遇到闭合符挡路时的拆行/填充策略”，不引入新的批量写入行为。

# 方案概览

名称：**智能守卫与单向推进策略（Smart Guard & Forward‑Only Split）**

核心思路：

当当前行尾部存在“挡路”的闭合符号（`}` / `)` / `]` 等）且与目标行不一致时，不再一律拆行，而是先进行一次**身份查验**，区分：

- **刚性配对（骨架内填充）**：闭符与同一行内的最近开符对应，说明是自动配对刚生成的骨架，应当在符号之间继续填目标字符。
- **残留粘连（尾巴推走）**：闭符没有对应开符且本行除缩进外无内容，说明是上一块结构的尾巴，应当拆行把它推到下一行。

同时，对“残留粘连”的拆行采取 **只推不退（Forward‑Only）**：拆行后不回退光标，避免拆行链式循环。

# 详细决策流程

## 触发条件

在 Gap Detection 的“行不匹配 / 字符不匹配”路径中，当检测到：

- `currentLine` 的尾部（去除右侧空白）存在 **连续闭合符**；且
- `targetLine` 在对应位置还有非闭合字符需要输入；即闭合符阻挡了目标内容的进入。

## 第一步：身份查验（你是谁？）

对当前行尾部闭合符进行定位：

1. 令 `currentTrimmedEnd = currentLine.trimEnd()`。
2. 计算 `trailingClosings = currentTrimmedEnd` 末尾连续闭合符序列。
3. 得到 `currentWithoutClosings`（去掉末尾闭合符后的左侧内容）。

查验标准（收紧，避免误判）：

- 取 `currentWithoutClosings` 的 **最后一个非空白字符** `lastNonWsChar`；
- 若 `lastNonWsChar` 是对应的开符（`(` / `{` / `[`），则认为末尾闭符属于同一行内的**刚性配对骨架**。
- 否则认为闭符是**残留尾巴**或不属于该层级。

额外约束（与目标对齐）：

- 只有当 `currentWithoutClosings.trimEnd()` 是 `targetLine.trimEnd()` 的前缀时，刚性配对才成立；否则一律按残留处理。
- 若目标在开符后立刻也是闭符（目标为“空配对”），视为已对齐，不进入填充。

## 第二步：分流决策

### 场景 A：刚性配对（有开符）

判定：

- `lastNonWsChar` 为对应开符；且
- `currentWithoutClosings` 是 `targetLine` 的前缀；且
- 目标下一个字符不是闭合符。

动作（豁免拆行）：

- **不插入换行**；
- 直接在 `currentWithoutClosings.length` 的位置插入目标的下一个字符；
- 让自动配对骨架持续向目标内容“自洽收敛”。

结果：

- `()` → `(t` → `(type: ... )`  
- `{}` → `{<content>}`（含智能 `{` 展开时的跨行补全）

### 场景 B：残留粘连（无开符 + 只有缩进）

判定：

- `currentWithoutClosings.trim().length === 0`（本行只有缩进与闭符）；且
- `targetLine.trim().length > 0`（目标行要求这里有实际内容）；且
- 目标行不是“纯闭合符行”。

动作（强制拆行）：

- 在闭符前插入 `\n + currentIndent`（使用当前行缩进，保证尾巴落位一致）；
- 把闭符整体推到下一行，为当前行腾出空间输入目标内容。

结果：

- `    }` + 目标 `    if (...) {`  
  → 插入新行后变为  
  `\n    }`（尾巴下沉）  
  当前行开始正常补 `if`。

## 第三步：防死循环机制（只推不退）

对场景 B 的拆行：

- **绝不设置 `cursorBackOffset`**；
- 让光标自然落在新行（Line N+1）开头。

原理：

- 拆行后的下一帧扫描，光标所在行是“干净的空/缩进行”，不会再次命中残留闭符拆行条件；
- 算法因此进入正常逐字符填充路径，彻底切断  
  `拆行 → 回退 → 再拆行` 的循环链。

与现有插入历史保护协同：

若同一 offset 在短时间内连续出现“`换行 + 缩进 + 自动配对骨架`”模式 ≥ 3 次，可直接降级为 mismatch/warning，避免保护触发前的大量噪声输出。

# 与现有代码的融合位置（设计级）

仅调整 `SmartReplaceHandler.computeNextGap` 的 Gap 决策顺序：

- 在“检测到行末 trailing closings”分支中（现有 Scenario A/B 与 High‑Priority Guard 区域），加入“身份查验 + 场景 A 豁免拆行”的优先判断。
- 场景 B 的拆行保持为“Forward Split”，但确保其触发条件严格限定为“纯缩进 + 残留闭符”。
